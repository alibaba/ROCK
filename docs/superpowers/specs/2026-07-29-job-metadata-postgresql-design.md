# Job Metadata PostgreSQL Storage Design

## 1. Goal

Replace the ROCK SDK Job metadata storage that currently persists JSON documents
to OSS with a PostgreSQL-backed repository.

The SDK runs inside a trusted metadata service. Database credentials are owned by
that service and are injected into the SDK through a SQLAlchemy session factory.
External users do not connect to PostgreSQL and do not receive database
credentials.

This change covers Job and Job Group metadata only. Logs, trajectories,
`result.json`, and other large artifacts remain in OSS.

## 2. Scope and constraints

- PostgreSQL is the production database.
- The SDK talks directly to PostgreSQL through SQLAlchemy.
- A Job may exist without a Group.
- A Job belongs to at most one Group.
- A Group contains zero or more Jobs.
- Within a Group, one non-null task ID identifies one stable Job row.
- Job names are not unique, including within the same namespace and experiment.
- `job_id` and `group_id` use PostgreSQL's native 128-bit `UUID` type.
- UUID values are generated by the SDK before insertion.
- Environment variables, credentials, labels, and speculative extension fields
  are not persisted.
- OSS metadata is not used as a write fallback.
- Historical OSS migration is outside this change.

## 3. Alternatives considered

### 3.1 Two tables with Group membership on Job — selected

Store Groups in `job_group_metadata` and Jobs in `job_metadata`. The nullable
`job_metadata.group_id` foreign key represents membership.

This matches the current one-Group-per-Job behavior and avoids an additional
membership table and join.

### 3.2 Separate Group membership table — rejected

A `job_group_member` table would support one Job in multiple Groups and
membership-specific attributes. Neither behavior is currently required, so the
extra table, repository methods, and transaction boundaries would be unused
complexity.

### 3.3 Single JSONB document table — rejected

Storing the former OSS documents as JSONB would minimize mapping work but weaken
status, Group membership, resume, and aggregate queries. It would also preserve
the same document-level overwrite behavior that the database migration is meant
to improve.

## 4. Database schema

### 4.1 `job_group_metadata`

The Group table stores only Group identity, scope, lifecycle, and dataset
location. Counts and score summaries are derived from `job_metadata`.

```sql
CREATE TABLE job_group_metadata (
    group_id       UUID PRIMARY KEY,
    namespace      VARCHAR(128) NOT NULL,
    experiment_id  VARCHAR(128) NOT NULL,
    mode           VARCHAR(16) NOT NULL,
    status         VARCHAR(32) NOT NULL,
    dataset        VARCHAR(512),
    split          VARCHAR(128),
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at    TIMESTAMPTZ
);

CREATE INDEX ix_job_group_scope_created
    ON job_group_metadata(namespace, experiment_id, created_at DESC);

CREATE INDEX ix_job_group_scope_status
    ON job_group_metadata(namespace, experiment_id, status);
```

| Column | Meaning |
|---|---|
| `group_id` | Stable SDK-generated Group identifier. It replaces the timestamp-based OSS `run_id`. |
| `namespace` | Tenant or business isolation scope. |
| `experiment_id` | Experiment isolation scope. |
| `mode` | Execution mode: `single`, `multi`, or `full`. |
| `status` | Group lifecycle status. |
| `dataset` | Optional dataset identifier used by resume. |
| `split` | Optional dataset split used by resume. |
| `created_at` | Group creation time and default list ordering field. |
| `updated_at` | Time of the most recent Group metadata update. |
| `finished_at` | Terminal completion time, otherwise null. |

Supported Group statuses are `planning`, `running`, `completed`, `partial`,
`failed`, and `cancelled`.

### 4.2 `job_metadata`

The Job table uses `job_id` as its only identity. Namespace, experiment, and Job
name are query attributes and may repeat.

```sql
CREATE TABLE job_metadata (
    job_id         UUID PRIMARY KEY,
    namespace      VARCHAR(128) NOT NULL,
    experiment_id  VARCHAR(128) NOT NULL,
    job_name       VARCHAR(255) NOT NULL,
    group_id       UUID,
    task_id        VARCHAR(255),
    job_type       VARCHAR(32) NOT NULL,
    status         VARCHAR(32) NOT NULL,
    sandbox_id     VARCHAR(128),
    session        VARCHAR(128),
    pid            BIGINT,
    exit_code      INTEGER,
    score          DOUBLE PRECISION,
    error          TEXT,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    started_at     TIMESTAMPTZ,
    finished_at    TIMESTAMPTZ,
    FOREIGN KEY (group_id)
        REFERENCES job_group_metadata(group_id)
        ON DELETE SET NULL
);

CREATE INDEX ix_job_scope_name_created
    ON job_metadata(namespace, experiment_id, job_name, created_at DESC);

CREATE UNIQUE INDEX uq_job_group_task
    ON job_metadata(group_id, task_id)
    WHERE group_id IS NOT NULL AND task_id IS NOT NULL;

CREATE INDEX ix_job_group_status
    ON job_metadata(group_id, status);

CREATE INDEX ix_job_sandbox
    ON job_metadata(sandbox_id)
    WHERE sandbox_id IS NOT NULL;
```

| Column | Meaning |
|---|---|
| `job_id` | Stable SDK-generated Job identifier used for exact reads and updates. |
| `namespace` | Job tenant or business scope. |
| `experiment_id` | Job experiment scope. |
| `job_name` | User-visible, non-unique Job name. |
| `group_id` | Nullable Group foreign key; null for a standalone Job. |
| `task_id` | Optional dataset task represented by this Job. |
| `job_type` | Execution implementation such as `bash` or `harbor`. |
| `status` | Current Job lifecycle status. |
| `sandbox_id` | Sandbox identifier required for resume. |
| `session` | Sandbox process session required for resume. |
| `pid` | Sandbox process ID required for resume. |
| `exit_code` | Terminal process exit code. |
| `score` | Terminal Job score. |
| `error` | Failure or unrecoverable reason. |
| `created_at` | Metadata creation time. |
| `updated_at` | Most recent metadata update time. |
| `started_at` | Job execution start time. |
| `finished_at` | Job terminal completion time. |

Supported Job statuses are `planned`, `starting`, `sandbox_ready`, `running`,
`completed`, `failed`, `cancelled`, and `unrecoverable`.

There is intentionally no unique constraint on namespace, experiment, Job name,
or any combination of those attributes. Exact mutations require a `job_id`;
attribute-based APIs return a list. A non-null task ID is unique within a Group
because the existing run model exposes one current Job per task. Resume updates
that stable Job row rather than inserting retry-history rows.

## 5. SDK model changes

`JobMeta` becomes the database-facing Job DTO:

- Add required `job_id: UUID`, generated with `uuid4`.
- Replace `run_id` with nullable `group_id: UUID`.
- Retain only columns represented by `job_metadata`.
- Change stored timestamps from strings to timezone-aware `datetime`.
- Remove `schema_version`, `attempt`, `status_reason`, `user_id`, `image`,
  `labels`, `env`, `tmp_file`, and `script_path`.

`RunMeta` remains the compatibility name used by the CLI, but its persisted
identity is a required `group_id: UUID`. A `run_id` read-only compatibility
property returns `group_id`. The following fields are query projections rather
than stored Group columns:

- `total_tasks`
- `pending_tasks`
- `task_job_map`
- `summary`

`task_job_map` maps each task ID to a Job UUID, not a non-unique Job name.

## 6. Repository boundaries

The SDK exposes a synchronous SQLAlchemy repository. The metadata service owns
the engine, pool, credentials, lifecycle, and any async thread dispatch.

The repository constructor accepts a configured `sessionmaker`:

```python
repository = JobMetadataRepository(session_factory)
```

The repository does not read database environment variables and does not create
production tables automatically. It exports SQLAlchemy metadata so that the
service's migration tooling can create the two tables. Unit tests may call
`Base.metadata.create_all`.

### 6.1 Job operations

- `create_job(meta: JobMeta) -> JobMeta`
- `get_job(job_id: UUID) -> JobMeta | None`
- `list_jobs(query: JobQuery) -> list[JobMeta]`
- `update_job(job_id: UUID, changes: JobMetaUpdate) -> JobMeta`
- `list_group_jobs(group_id: UUID) -> list[JobMeta]`

`JobQuery` supports optional `namespace`, `experiment_id`, `job_name`,
`group_id`, `task_id`, and `status` filters plus deterministic created-time
pagination.

`JobMetaUpdate` accepts only mutable runtime fields: `status`, `sandbox_id`,
`session`, `pid`, `exit_code`, `score`, `error`, `started_at`, and
`finished_at`. `updated_at` is set by the repository.

### 6.2 Group operations

- `create_group(meta: RunMeta) -> RunMeta`
- `create_group_with_jobs(meta: RunMeta, jobs: list[JobMeta]) -> RunMeta`
- `get_group(group_id: UUID) -> RunMeta | None`
- `list_groups(query: GroupQuery) -> list[RunMeta]`
- `update_group(group_id: UUID, changes: GroupMetaUpdate) -> RunMeta`
- `resolve_group_id_for_resume(scope) -> UUID | None`
- `find_completed_tasks(group_id: UUID) -> set[str]`

Group projections are calculated from Job rows:

```sql
SELECT
    COUNT(*) AS total_tasks,
    COUNT(*) FILTER (
        WHERE status NOT IN ('completed', 'failed', 'cancelled', 'unrecoverable')
    ) AS pending_tasks,
    COUNT(*) FILTER (WHERE status = 'completed') AS completed,
    COUNT(*) FILTER (WHERE status IN ('failed', 'unrecoverable')) AS failed,
    COALESCE(AVG(score), 0) AS avg_score,
    COALESCE(SUM(score), 0) AS total_score
FROM job_metadata
WHERE group_id = :group_id;
```

## 7. Write and update flow

Creating a run uses one transaction:

1. Generate one Group UUID.
2. Insert the Group.
3. Generate one Job UUID per planned task.
4. Insert all planned Job rows with the Group UUID.
5. Commit.

These steps are exposed as `create_group_with_jobs` so the Group and initial
planned Jobs cannot become partially visible.

Runtime callbacks retain the same Job UUID and issue field-level updates:

1. Job starts: update status, Sandbox ID, session, PID, and start time.
2. Job completes: update status, exit code, score, error, and finish time.
3. Resume: query Group Jobs, recover Jobs with a resumable status and complete
   Sandbox process coordinates.
4. Group finishes: update Group status and finish time. Aggregate fields are
   calculated when the Group is read.

The repository never locates a mutable Job by name. A name query may return
multiple rows, while an update always requires `job_id`.

## 8. Error and transaction behavior

- Duplicate `job_id` or `group_id` raises `MetadataConflictError`.
- Updating an unknown UUID raises `MetadataNotFoundError`.
- Assigning a nonexistent Group raises `MetadataConstraintError`.
- Assigning a Job to a Group in a different namespace or experiment raises
  `MetadataConstraintError` before commit.
- SQLAlchemy exceptions are rolled back and wrapped in a metadata repository
  exception while preserving the original exception as the cause.
- A metadata update either commits all supplied fields or commits none.

## 9. OSS compatibility

PostgreSQL is the sole source of truth for Job and Group metadata after this
change. `JobViewer` continues to read artifacts and logs from OSS but no longer
owns `write_job_meta`, `get_job_meta`, `write_run_meta`, `get_run_meta`, or
`list_runs`.

No dual-write is performed. No automatic fallback to OSS is performed. Existing
OSS metadata can be migrated by a separate one-time tool if required later.

## 10. Testing

Tests cover:

- ORM schema, PostgreSQL-compatible UUID columns, foreign keys, and indexes.
- Standalone and grouped Job creation.
- Duplicate Job names with distinct UUIDs.
- Exact Job reads and updates by UUID.
- Attribute queries returning multiple Jobs.
- Group Job listing and task mapping.
- Derived Group totals, pending count, score summary, and completed tasks.
- Resume selection and recoverable process fields.
- Cross-scope Group assignment rejection.
- Transaction rollback on conflicts and constraints.
- CLI orchestration retaining a stable Job UUID across planned, running, and
  terminal updates.
- Confirmation that metadata code performs no OSS reads or writes.
